# v0.2 Cleanup + Init Skill

Closes the four remaining v0.2 surface items before the eval pass and B-core
archive. Source: `docs/plans/2026-05-22-v0.2-plan.md` (B-cleanup + the one
B-integrate item the owner kept — `codocu.md` auto-load via CLAUDE.md).

Parked items, deliberately out of scope: `voice.md` finishing (parked pending
learning-skill work), post-impl verification, specialist-skill composition,
METADOCU leakage guard.

A fifth deliverable added 2026-05-25 after testing surfaced the install-mode
gap: relocate runtime skill assets so a marketplace install can reach them.

## Deliverables

### 1. `README.md` — v0.2 rewrite

Drops the three-state model and the v0.1 command table. Replaces with v0.2's
doc-first framing: `/codocu` (the main skill — write, review, place, verify) and
`/codocu:fold` and `/codocu:init` as siblings. Keep the "who it's for", "prior
art", and "install & use" sections; rewrite their internals only where they
quote v0.1 vocabulary.

### 2. Archive `docs/design/flows.md`

Move to `docs/archive/2026-05-25-flows-deprecated.md`. The file already carries
`// deprecate?` at line 1 and still teaches sync states. v0.2 dropped the state
machine — flows.md no longer reflects reality and shouldn't be loaded by
contributors as design truth.

Grep for references first; the only live reference is `codocu.md` line 24
("the old `flows` spec is being reworked in v0.2 — flow overlays become
optional helpers, not a standing authority"). Update that line to drop the
"being reworked" framing and point at the archive for history.

### 3. Refresh `templates/codocu.md` with real defaults

Drop the sync-state marker line (`> Codocu sync state: TBD`). The binary
inited/uninited model in v0.2 doesn't need a state line.

Fill the template with concrete defaults so init can describe the conventions
in plain language, not just list headings. Settled defaults (revised during
testing 2026-05-25):

- Docs layout: `docs/systems/` (long-term home), `docs/plans/` (fleeting
  working plans), `docs/archive/` (folded plans, never hand-edited).
- Tech-debt: optional. `docs/tech-debt.md` one-line entries:
  `**<TD-short-id>**: <what is wrong> - <optional: reason || solution draft>`.
- Fold settings: ask per incomplete plan whether to archive as-is, extract
  incomplete parts, or leave.
- Agent guidelines lifted from this repo's `codocu.md`.

**Meta-comment convention.** The template carries `<!-- codocu:init <instruction> -->`
comments that init reads, acts on, and strips from the written file (e.g.
asking the user whether to include the optional Tech Debt section). Plain
HTML comments are left in place. See the init skill body for handling.

Also create `templates/tech-debt.md` — a minimal catchall with the one-line
entry format in a comment block and `## Backlog` as the only heading.

### 4. Build `/codocu:init` skill

A sibling skill to `/codocu`. Lives at `skills/init/SKILL.md`.

**What it does, in order:**

1. Read `templates/codocu.md` and `templates/tech-debt.md`. Parse
   `codocu:init` meta-comments. Show a welcome that describes the conventions
   in plain language (where docs live, the optional tech-debt catchall, fold
   behavior, the `@codocu.md` wiring) — not the template headings. Fold any
   meta-comment questions (e.g. "include tech-debt?") into the same welcome.
   Ask once: OK, or corrections first?
2. Apply any corrections and meta-comment answers to the in-memory templates;
   strip all `codocu:init` comments.
3. Write `codocu.md` to the target repo root, and `docs/tech-debt.md` if the
   user opted in.
4. Append `@codocu.md` to `CLAUDE.md`. Create `CLAUDE.md` with that single
   line if it doesn't exist; no-op if the line is already present.
5. Offer the orientation handoff: "Want a doc-system orientation pass?" If
   yes, invoke `/codocu` with a prompt asking it to orient around the repo
   and suggest 1–2 clustering strategies for long-term docs under
   `docs/systems/` (inline only, no files). If no, init ends.

**Idempotency.** If `codocu.md` already exists, do not overwrite. Surface
("This repo is already inited — `codocu.md` exists. Re-run will not overwrite.
Edit `codocu.md` directly to revise conventions.") and stop. If
`docs/tech-debt.md` already exists, leave it alone. If `CLAUDE.md` already
contains `@codocu.md`, no-op on the append.

**Voice.** Carries the same voice anchor as `/codocu`'s SKILL.md. No
narration of internal steps, no menu-listing the template fields.

### 5. Relocate runtime skill assets

In dev (`--plugin-dir`), skills can read from `docs/corpus/*` and
`templates/*` because cwd is the plugin repo. In a real install, cwd is the
user's project — those paths resolve into the user's tree and fail. Move the
runtime assets into the skill directories so they're always reachable
relative to `SKILL.md`:

- `templates/codocu.md` → `skills/init/templates/codocu.md`
- `templates/tech-debt.md` → `skills/init/templates/tech-debt.md`
- `docs/corpus/{placement-rules,voice-pairs,smell-catalog}.md` →
  `skills/codocu/references/`
- `docs/design/{principles,voice,doc-standard}.md` →
  `skills/codocu/references/`

`docs/corpus/{eval-fixtures,improvement-notes}.md` stay put — not loaded at
runtime. `docs/design/build-skill/` stays put — deferred Track C.

`agents/codocu-reviewer.md` cross-references `skills/codocu/references/`
rather than duplicating its two files; same plugin, same install root.

Contributors now read the design specs at `skills/codocu/references/`
instead of `docs/design/`. The codocu skill is the canonical home for what
governs the agent at runtime — moving them there makes that explicit and
single-sourced. `codocu.md` and `CLAUDE.md` updated to point at the new
location.

## Decisions

- **One spec for all four items.** They share the v0.2-ship goal and
  cross-reference each other (init writes the template, archiving flows.md
  affects what codocu.md should reference).
- **No separate implementation plan.** The work is mechanical enough that the
  spec is the plan. The deliverables above are the checklist.
- **Init does not scan the repo or ask discovery questions.** Pure scaffold +
  the welcome-and-confirm gate.

## Done test

Run by hand in a fresh test repo:

- `claude --plugin-dir <codocu repo> /reload-plugins` reports `init` as a
  loaded skill.
- `/codocu:init` in an empty repo: welcome describes the conventions in plain
  language (not headings); `codocu.md` and `docs/tech-debt.md` written;
  `CLAUDE.md` created with `@codocu.md`.
- Re-run on the same repo: no-op with a clear message.
- `/codocu:init` in a repo that already has `CLAUDE.md`: `@codocu.md` appended,
  rest of `CLAUDE.md` untouched.
- `README.md` skim: no v0.1 vocabulary anywhere (no "Synced", "Desynced",
  "Dirty", `:propose`, `:doc-code`, `:code-doc`, `:apply` outside the prior-art
  block).
- `docs/design/flows.md` no longer exists; archive copy does; `codocu.md` no
  longer references the live path.
- `templates/codocu.md`: no sync-state line.

## Reader test

A contributor reading this spec for the first time: where do they get lost or
bored? The init section is the only place with real procedure — the rest is
"do the thing." If init's step list reads like ceremony, cut it to the four
moves that matter (read template, preview-and-confirm, write codocu.md,
append to CLAUDE.md).
